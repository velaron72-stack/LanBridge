# LanBridge 2.0.0

Виртуальная локальная сеть между двумя Android-устройствами без сервера и без root. Игры и приложения, которые работают только по LAN, видят друга как устройство в той же сети: unicast, broadcast, multicast, TCP, UDP (в том числе с IP-фрагментацией), ICMP.

Ролей «хост/клиент» нет: оба устройства выполняют один и тот же код, «инициатор» рукопожатия выбирается автоматически сравнением открытых ключей. Пароля нет: устройства узнают друг друга по открытым ключам из обмененных кодов.

## Использование

1. Оба: «Создать код».
2. Обменяться кодами (текст или QR), вставить код друга.
3. Оба: «Подключиться» (с разницей не больше минуты).
4. После статуса «Подключено» запускать игру. «Проверка LAN» показывает, проходят ли unicast (по виртуальному и по реальному адресу), broadcast, multicast, UDP 4000 Б (фрагменты) и TCP 256 КБ.
5. Если игра не стартует: на обоих устройствах «Журнал и потоки» (значок с ключом) → «Сбросить потоки»; запустить игру, дождаться зависания, снова открыть «Журнал и потоки» → «Копировать». Там видно, какие потоки (протокол, адреса, порты, размеры пакетов, флаги TCP) идут через туннель, первые и последние пакеты по времени и что отброшено. «Проверка LAN» до копирования не нажимать: она добавляет свой трафик (порт 41377 в списках не показывается, но считается).

При каждом запуске показывается окно «Приложение в разработке» (кнопки «ОК» и «Настройки»). В настройках: отключение оптимизации батареи и разрешение работы в фоне.

## Две адресации в одном туннеле

- Виртуальная сеть `192.168.x.0/24` (два адреса), выбирается детерминированно и не пересекается с реальными адресами устройств.
- Зеркалирование реальных адресов. Адреса интерфейсов устройств (например, Wi-Fi) передаются в коде. Адрес друга маршрутизируется в туннель как `/32`, собственный реальный адрес добавляется на TUN первым (основным). Поэтому игра, которая привязывается к адресу Wi-Fi или сообщает его другому игроку, работает без подмены адресов: источник и назначение пакетов остаются настоящими, ответы находят свой сокет. Адреса, совпадающие с адресами другой стороны, шлюзы, DNS, `.0/.1/.254/.255` внутри общей сети в маршруты не попадают.

Если система не принимает TUN с реальными адресами, служба создаёт его без них (только виртуальная сеть).

Источник ответов UDP. Android берёт первый адрес TUN источником для всех пакетов, которые через него уходят (маршруты VPN добавляются без предпочитаемого источника). Но ответ сервера должен прийти с того адреса, на который обратился друг, иначе сокет с `connect()` и протоколы с проверкой адреса отправителя (например, ENet) его отбросят. Движок запоминает для каждого потока UDP (локальный порт, адрес и порт друга), на какой из наших адресов пришёл пакет, и ставит этот адрес источником ответа, как это делает `IP_PKTINFO`; фрагменты больших ответов получают тот же адрес. «Проверка LAN» считает ответ с чужого адреса ошибкой.

## Сборка

GitHub: залить содержимое репозитория, открыть Actions → Build APK → artifact `LanBridge-apk` (подписанный release APK). Ключ подписи лежит в `keystore/` (постоянный, чтобы новые сборки ставились поверх старых; проект не публичный).

Локально: JDK 17, Android SDK 35, NDK 26.3.11579264, CMake 3.22.1, Gradle 8.9.

```bash
gradle :app:assembleRelease
```

## Устройство

| Слой | Файлы | Задача |
|---|---|---|
| Native (C++17, без зависимостей) | `app/src/main/cpp` | криптография, формат кода, STUN, рукопожатие, hole punching, пересылка пакетов TUN ↔ UDP, очередь отправки, счётчики потоков |
| Kotlin core | `core/` | JNI, настройки, состояние UI, проверка LAN |
| VPN-служба | `vpn/TunnelVpnService.kt` | TUN-интерфейс, `protect()` сокета, foreground-уведомление, wake/wifi lock |
| UI (Compose) | `ui/` | код/QR, статус, настройки, журнал и потоки, справка |

Протокол: Noise_KK-подобное рукопожатие (X25519, BLAKE2s, ChaCha20-Poly1305), защита от повторов (окно 2048), смена ключей каждые ~2 минуты, keepalive, измерение RTT. Код соединения (`LB2-…`): версия, срок, открытый ключ, тип NAT, имя, до 8 адресов, контрольная сумма. Коды версии 1.x (`LB1-…`) не принимаются.

В TUN маршрутизируются только виртуальная подсеть, `224.0.0.0/4`, `255.255.255.255/32` и реальные адреса друга; остальной трафик телефона не затрагивается.

## Тесты

```bash
bash native-tests/run.sh               # модульные и интеграционные тесты ядра, ASan + UBSan
sudo python3 native-tests/nettest.py   # реальное ядро Linux: TUN в двух сетевых пространствах имён (root, /dev/net/tun)
```

`run.sh`: известные ответы (RFC 7693, 7748, 8439, независимые эталоны), рукопожатие (подмена, неверный PSK, привязка ответа), окно повторов, формат кода и фаззинг декодера, STUN через локальный mock, два движка в одном процессе: unicast, broadcast, multicast, зеркалирование реальных адресов, перезапись источника, MTU-пакеты, отбрасывание чужого трафика, 3000 мусорных датаграмм, выход друга, посторонний пир, таймаут и повтор, смена ключей под нагрузкой.

`nettest.py`: настоящие TCP (8 МБ, 20 параллельных соединений, оба направления), UDP-эхо от 32 до 60000 байт (фрагментация), UDP с `connect()`, поток 12 Мбит/с, снимок 400 пакетов, ICMP, broadcast, directed broadcast, multicast; для зеркалированных адресов дополнительно: сервер, привязанный только к реальному адресу, клиент, привязанный к реальному адресу, ответы с правильным источником.

## Не включено намеренно

R8 (сжатие, оптимизация, обфускация) и трёхэтапный CI с проверками R8/JNI: решено отложить. Обфускация закрывает только слой Kotlin, ядро на C++ она не трогает (там уже скрыты символы и убрана отладочная информация), секретов в приложении нет, а пока идёт отладка игровой совместимости обфусцированные трассировки только мешали бы. Вернуться перед публичным релизом.

## Ограничения

- Прямое соединение невозможно, если NAT симметричный у обеих сторон (часть мобильных операторов). Обход: один Wi-Fi или точка доступа.
- Только IPv4 и уровень IP без root. Игры, жёстко привязанные к интерфейсу Wi-Fi (`SO_BINDTODEVICE`, `Network.bindSocket`) или использующие не-IP протоколы, работать не будут. Другой VPN одновременно включить нельзя.
- Если у обоих устройств совпадает реальный адрес, он не зеркалируется (остаётся виртуальная сеть).
- Производители (Xiaomi, Huawei/Honor, Oppo/Realme, Vivo, Samsung) агрессивно убивают фоновые службы: нужны автозапуск и снятие ограничения батареи (Настройки → Фоновая работа).
- Android-часть (Gradle, CMake/NDK, Kotlin, Compose) в окружении разработки не собиралась; проверена нативная логика на хосте и реальным ядром Linux. Первая сборка в Actions — реальная проверка компиляции.
